1. What Is a Mobile Application?

A mobile application is a software program designed to run on a handheld device — a smartphone or tablet. Unlike desktop software, mobile apps must operate under constraints that do not exist on a laptop:

  • Limited battery — CPU-heavy work drains power fast
  • Limited memory (RAM) — the OS can kill your app without warning if RAM is low
  • Variable connectivity — the network can drop at any moment
  • Small screen — UI must be designed for touch and compact layouts
  • Background restrictions — apps are not always running; the OS may suspend them
  • Privacy & permissions — apps must ask the user before accessing camera, location, contacts, etc.

Every well-built mobile app is designed with these constraints in mind. The standard way to handle this complexity is to split the app into layers, each with a single clear responsibility.

2. The Three-Layer Architecture

Almost every mobile app — regardless of the platform (iOS, Android, Flutter) or the company that built it — is organised into three layers:

┌──────────────────────────────────────────────────────┐
│           Presentation Layer (UI)            │
│  Screens · Widgets · Navigation · Animations    │
│    What the user sees and touches             │
├──────────────────────────────────────────────────────┤
│           Business Logic Layer              │
│  State Management · Rules · Validation · Auth   │
│    What the app decides and calculates         │
├──────────────────────────────────────────────────────┤
│           Data Layer                      │
│  Network · Local Storage · Device APIs         │
│    Where the app gets and stores data          │
└──────────────────────────────────────────────────────┘

Presentation Layer

  • Screens & pages
  • Buttons, forms, lists
  • Navigation between screens
  • Animations & transitions
  • Theme & styling

In our app: home.dart, login_screen.dart, all widgets

Business Logic Layer

  • State management
  • Form validation rules
  • Authentication logic
  • Cart calculations
  • Decision making

In our app: auth_provider.dart, cart_provider.dart

Data Layer

  • API / HTTP calls
  • Local database
  • SharedPreferences
  • File system
  • Device sensors

In our app: product_service.dart, auth_service.dart, user_storage.dart

Why layers? Layers keep code organised. The UI should not make API calls directly — it should ask the Business Logic layer, which asks the Data layer. This way, if you switch from REST to GraphQL tomorrow, you only change the Data layer — the UI and the business logic don't need to know.

3. Component 1 — User Interface (UI)

The UI is what the user sees and touches. Every mobile app's UI consists of a fixed set of building blocks regardless of which platform or framework you use:

Building Block Description iOS Name Android Name Flutter Name
Screen / Page A full-screen view the user navigates to ViewController Activity / Fragment Screen Widget
List Scrollable collection of repeated items UITableView RecyclerView ListView
Form input Text field, checkbox, dropdown UITextField EditText TextField
Button Tappable action trigger UIButton Button ElevatedButton
Image Displays a picture (local or from URL) UIImageView ImageView Image.network()
Bottom Navigation Tab bar at the bottom of the screen UITabBarController BottomNavigationView BottomNavigationBar

Navigation

Navigation is the system that moves the user from one screen to another. Every platform has two models:

Stack Navigation (Push / Pop)

Screens stack on top of each other like a deck of cards. Tapping Back removes the top screen.

Used for: detail pages, checkout flows, settings sub-pages.

Flutter: Navigator.push() / Navigator.pop()

Tab Navigation

Multiple top-level sections accessible from a persistent bottom bar. Switching tabs doesn't push/pop.

Used for: Home, Search, Cart, Profile — the main sections of an app.

Flutter: IndexedStack + BottomNavigationBar

4. Component 2 — Business Logic

Business logic is the brain of the app. It does not display anything — it makes decisions. Examples of business logic:

  • Is this email address valid?
  • Is the user's session token still valid?
  • What is the total price of the items in the cart?
  • Should this button be enabled or disabled right now?
  • If a network call fails, should we retry or show an error?

State Management

State is any data that can change and that the UI needs to react to. Every mobile app needs a strategy for managing state. Common approaches:

Approach Description Used In
Local state State lives in a single screen — other screens can't see it A toggle switch, a form field value
Shared / global state State lives in a central place — all screens can read and update it Auth status, cart contents, theme choice
Server state Data fetched from an API — needs to be cached and refreshed Product list, user profile from a backend
In our app: We used setState() for local state (form fields, loading flags) and Provider (ChangeNotifier) for global shared state (cart, authentication, theme). This is exactly the business logic layer.

5. Component 3 — Data Storage

Mobile apps need to store data locally on the device. There are four types, each suited to different needs:

Storage Type What It Stores Persistent? Example Use Flutter / Android / iOS
Key-Value Store Simple settings: strings, booleans, numbers Yes Auth token, dark mode setting, user preferences SharedPreferences / UserDefaults / NSUserDefaults
Relational Database Structured tables with relationships Yes Offline product catalogue, chat messages, notes sqflite / SQLite / Core Data
File System Any file: images, PDFs, audio, video Yes Downloaded files, cached images, exported reports path_provider / File APIs
In-Memory (RAM) Temporary data during app session No — lost on close Search results, current page's product list Variables / List / Map

When to use which?

"Is the data small and simple?" → YES → Key-Value Store (SharedPreferences)
"Is the data structured and needs querying?" → YES → SQLite Database
"Is the data a file (image, PDF, audio)?" → YES → File System
"Is the data only needed while the app is open?" → YES → In-Memory variable

6. Component 4 — Networking

Most mobile apps are clients — they send requests to a server (backend) and receive responses. This client–server communication happens over the internet using standard protocols.

The Client–Server Model

┌──────────────────┐          ┌──────────────────────┐
│ Mobile App │          │ Backend Server │
│ (Client) │ ─── Request ──→ │ (e.g. dummyjson.com)│
│ │ ←── Response ── │ │
└──────────────────┘          └──────────────────────┘
                    ↕ Internet (HTTP/HTTPS)

REST API — the most common standard

REST (Representational State Transfer) is the dominant style for mobile–backend communication. It uses HTTP methods to describe what action to perform:

HTTP Method Meaning Example
GET Read data GET /products → get all products
POST Create new data POST /orders → place a new order
PUT / PATCH Update existing data PUT /users/5 → update user 5's profile
DELETE Remove data DELETE /cart/item/3 → remove item from cart

Key networking concerns for mobile apps

  • Offline handling — the network can disappear at any moment; show a meaningful error, don't crash
  • Timeouts — if the server takes too long, give up and tell the user
  • HTTPS only — never send data over plain HTTP; always use encrypted HTTPS
  • Authentication headers — after login, every request must carry the token so the server knows who is asking
  • Caching — avoid repeating the same request; save the result and reuse it

7. Component 5 — Device APIs

A smartphone is far more than a small computer — it has hardware components that no desktop has. Mobile apps can access these through Device APIs provided by the operating system. The app must ask for permission before accessing most of them.

Device API What It Provides Example App Use Permission Needed?
Camera Take photos and videos Profile picture, document scan, QR code Yes
GPS / Location Current latitude & longitude Map apps, delivery tracking, store finder Yes
Push Notifications Messages sent from server to device Order updates, chat messages, news alerts Yes (iOS)
Biometrics Fingerprint / Face ID authentication App lock, payment confirmation Yes
Accelerometer / Gyroscope Device motion and orientation Step counter, game controls, screen rotation No (usually)
Contacts Phone address book Find friends, share contact details Yes
Microphone Record audio Voice search, voice messages, calls Yes
Bluetooth Short-range wireless communication Connect to headphones, smartwatch, IoT devices Yes
Always request only what you need. If your shopping app asks for access to Contacts and Location, users will be suspicious. Request only the permissions that are clearly necessary for your app's purpose. Both Apple and Google reject apps that over-request permissions.

8. Component 6 — Authentication & Security

Security in mobile apps works on multiple levels:

Authentication Methods

Method How it works Example
Username + Password User enters credentials; server checks and returns a token What we built in Lecture 13
Social Login Login via Google, Apple, Facebook — they handle the password "Sign in with Google"
OTP (One-Time Password) A code is sent via SMS or email; valid for a short time Bank apps, two-factor authentication
Biometric Fingerprint or Face ID — no password typed at all Unlock a banking app after initial login

Token Types

Session Token

A random string the server generates. The server stores a mapping of token → user. Simple, but requires the server to remember every active session.

Used by: reqres.in (what we built with)

JWT (JSON Web Token)

A self-contained token that encodes the user's identity inside it. The server doesn't need to store anything — it just verifies the signature.

Used by: most modern REST APIs

Secure Storage Rules for Mobile

  1. Never store passwords in plain text — only tokens should be stored after login
  2. Use the platform's secure storage for sensitive tokens (Keychain on iOS, Keystore on Android)
  3. Use HTTPS everywhere — plain HTTP exposes data to anyone on the same WiFi
  4. Do not log sensitive data — don't print tokens or passwords to the console in production

9. Component 7 — Push Notifications

Push notifications are messages sent from the server to the device, even when the app is not open. This is the opposite of the usual request–response model where the app asks first.

Normal flow (pull):
App → "Give me updates" → Server → "Here they are"

Push notification flow:
Server → "Here is an update for you" → Device → shows notification banner

How Push Works

  1. The app registers with the platform's notification service (APNs on iOS, FCM on Android)
  2. The platform gives the app a unique device token
  3. The app sends that token to your server
  4. When your server wants to notify the user, it sends the message to APNs/FCM along with the device token
  5. APNs/FCM delivers the notification to the device
Platform Notification Service Flutter Package
iOS APNs (Apple Push Notification service) firebase_messaging
Android FCM (Firebase Cloud Messaging)

10. Component 8 — App Lifecycle

A mobile app is not always "running" in the way a desktop app is. The operating system controls the app's lifecycle — it can pause, resume, or kill the app without warning. Understanding lifecycle is essential for building apps that behave correctly.

State What it means What you should do
Foreground App is visible; user is interacting Normal operation; update UI, play media
Background App is not visible but still running (briefly) Save state; pause heavy operations; stop the camera
Suspended / Killed OS has paused or terminated the app to free memory On next open, restore state from local storage
User opens app → Foreground
User presses Home button → Background
OS needs RAM → Killed (app process ended, data in RAM lost)
User taps app icon again → Foreground (app restarts from scratch)

↳ This is why we save important data to SharedPreferences or a database —
  RAM is not reliable across app sessions.
In our app: We already handle this correctly. The auth token is saved to SharedPreferences (Lecture 7), so when the OS kills and restarts the app, the user is still logged in. The theme choice (Lecture 14) is also persisted the same way.

Key Takeaway: Every mobile app — from a simple notes app to Instagram — is built from the same fundamental components: a UI layer, a business logic layer, and a data layer. The UI shows things, the business logic decides things, and the data layer stores and fetches things. Keeping these three concerns separate is what makes apps maintainable, testable, and scalable. Everything we have built so far fits neatly into this structure.
