1. What Is a Background Service?

In Lecture 16 we learned that a mobile app has a lifecycle: it can be in the foreground (visible), in the background (not visible but briefly running), or killed (process ended). A background service is code that runs even when the app is not visible to the user.

Without background services, apps could only do work while the user was actively looking at them. With background services, apps can:

  • Sync data with the server while the user is doing something else
  • Download a file after the user closes the app
  • Track location for a navigation or delivery app
  • Play music after the user switches to another app
  • Send a local reminder notification at a scheduled time
  • Upload photos to the cloud when connected to WiFi at night
Foreground Work vs Background Work

User opens app → taps "Download" → app visible → Foreground work
User presses Home → app hidden → download continues → Background work
User opens another app → your app is invisible → download still running → Background service
User's phone is on the charger at night → your app syncs data → Scheduled background task

2. Why Operating Systems Restrict Background Work

You might wonder: why can't apps just run in the background freely? The answer is that background work costs battery. Every instruction the CPU executes, every byte sent over the network, every GPS reading — all drain battery.

If every installed app ran freely in the background at all times:

  • A phone with 50 installed apps would drain in 2–3 hours
  • Users would uninstall any app they suspected of draining battery
  • The device would get hot

To protect the user, both Android and iOS introduced increasingly strict background execution limits over the years:

Year Platform Restriction Introduced
2016 Android 6 (Doze) Phone in standby → background network & CPU frozen
2017 Android 8 Background services killed after app is backgrounded; use JobScheduler
2019 Android 10 Background location heavily restricted; must show notification
2013 iOS 7 Background App Refresh introduced — OS decides when to run your task
2019 iOS 13 BGTaskScheduler replaces older APIs; strict time limits enforced
The OS is in charge — not your app. You cannot force a background task to run exactly when you want. You register a task and tell the OS your constraints (needs WiFi, needs charging, etc.). The OS decides the actual execution time based on battery level, network state, and what other apps are doing.

3. The Three Types of Background Work

Every background use case fits into one of three categories:

One-Time Task

A single piece of work that should complete even if the app is closed.

Examples: upload a photo, send a log report, sync after login

OS behaviour: runs once, retries on failure, then done

Android: OneTimeWorkRequest
iOS: BGProcessingTask

Periodic Task

Work that repeats on a schedule (e.g. every 15 minutes or every day).

Examples: sync emails, refresh news feed, backup data

OS behaviour: OS decides exact timing; minimum interval is 15 minutes

Android: PeriodicWorkRequest
iOS: BGAppRefreshTask

Foreground Service

Long-running work that the user is aware of — shown as a persistent notification.

Examples: navigation turn-by-turn, music playback, active download, fitness tracking

OS behaviour: runs until explicitly stopped; notification cannot be hidden

Android: ForegroundService
iOS: long-running background modes

Rule of thumb: If the user explicitly started an ongoing activity (navigation, music, workout), use a Foreground Service. If you need to do maintenance work while the user isn't watching (sync, backup), use a Periodic Task. If you need to finish something the user just triggered (upload a photo), use a One-Time Task.

4. How Android Handles Background Work — WorkManager

WorkManager is Google's officially recommended API for background work on Android. It is battery-aware, survives app restarts and device reboots, and handles retries automatically.

WorkManager Concepts

Concept What it is
Worker A class you write that contains the actual background code (what to do)
WorkRequest Describes when and how to run the Worker (one-time vs periodic, constraints)
Constraints Conditions that must be met before the task runs (WiFi, charging, storage available)
WorkManager.enqueue() Registers the task with the OS scheduler

How WorkManager decides when to run your task

Your app calls WorkManager.enqueue(myTask, constraints)
↓
WorkManager stores the task in a local SQLite database (survives reboots)
↓
OS checks constraints periodically:
"Is WiFi connected? Is battery above 20%? Is device idle?"
↓
All constraints met → OS wakes up your Worker → runs your code
↓
Worker returns SUCCESS or RETRY → WorkManager handles the result

WorkManager — Android Kotlin example (for understanding)

Android Kotlin — concept only, not Flutter code 
// Step 1: Define the Worker — what work to do
class SyncWorker(context: Context, params: WorkerParameters)
    : CoroutineWorker(context, params) {

  override suspend fun doWork(): Result {
    syncDataWithServer() // your actual work here
    return Result.success()   // or Result.retry() / Result.failure()
  }
}

// Step 2: Define constraints — conditions that must be true
val constraints = Constraints.Builder()
  .setRequiredNetworkType(NetworkType.CONNECTED) // needs internet
  .setRequiresCharging(true)                    // only when plugged in
  .build()

// Step 3: Schedule the task
val request = PeriodicWorkRequestBuilder<SyncWorker>(
    1, TimeUnit.HOURS // run every 1 hour (minimum is 15 minutes)
  )
  .setConstraints(constraints)
  .build()

WorkManager.getInstance(context).enqueue(request)

5. How iOS Handles Background Work — BGTaskScheduler

iOS is even more restrictive than Android about background execution. All background tasks must be registered in the app's Info.plist file before the app ships. The OS decides exactly when they run based on machine learning — it learns the user's habits (e.g. the user charges their phone at 11pm and checks news at 7am, so iOS runs a news refresh at 6:55am).

iOS Background Task Types

Task Type API Time Limit Best For
App Refresh BGAppRefreshTask ~30 seconds Quick data sync, fetch new content
Processing Task BGProcessingTask Minutes (device must be idle & charging) Heavy work: ML model updates, database migration
Background Mode Declared in Info.plist Unlimited (but scrutinised by App Store review) Audio, location, VoIP, Bluetooth — ongoing services
iOS time limits are hard. If your BGAppRefreshTask runs longer than ~30 seconds, iOS kills it. Apple's App Store review team rejects apps that abuse background modes (e.g. declaring location mode but not actually needing it). Every background mode you declare must be justified in your App Store submission.

6. Flutter — The workmanager Package

Flutter provides the workmanager package, which wraps WorkManager on Android and BGTaskScheduler on iOS behind a single Dart API. You write one piece of code and it works on both platforms.

Add the dependency

pubspec.yaml 
dependencies:
  workmanager: ^0.5.2

How workmanager works in Flutter

Your Dart code → workmanager.registerTask()
↓
On Android: registers with WorkManager
On iOS: registers with BGTaskScheduler
↓
OS decides when to run it
↓
OS launches a NEW Dart isolate (your main app may not be running!)
↓
Your callbackDispatcher function runs with the task name
↓
Task completes → Isolate shuts down
Critical point: When a background task runs, it starts a brand-new Dart Isolate — completely separate from your running app. This means your Providers, Navigator, BuildContext, and in-memory state are not available. The background task can only use packages that work without Flutter UI — like http, shared_preferences, or sqflite.

7. Step-by-Step: Scheduling a Background Sync Task

Let's implement a periodic background task that checks for new products every 15 minutes — even when the app is closed.

Step 1 — The callbackDispatcher (top-level function)

The callbackDispatcher is the entry point for all background tasks. It must be a top-level function (not inside any class) because it runs in a separate Isolate.

lib/main.dart (add at the top, outside main()) 
import 'package:workmanager/workmanager.dart';

// This is the function the OS calls when a background task fires.
// It MUST be a top-level function — not inside a class.
// It runs in its own Isolate — no access to app state or BuildContext.
@pragma('vm:entry-point') // tells Dart not to tree-shake this function
void callbackDispatcher() {
  Workmanager().executeTask((taskName, inputData) async {
    // taskName tells us which task was triggered
    switch (taskName) {
      case 'syncProducts':
        await _runProductSync();
        break;
      case 'dailyCleanup':
        await _runCleanup();
        break;
    }
    return Future.value(true); // true = success, false = failure (triggers retry)
  });
}

// The actual sync work — only uses http and SharedPreferences (no UI)
Future<void> _runProductSync() async {
  try {
    final products = await ProductService.getProducts();
    // Save the result to SharedPreferences or a local database
    final prefs = await SharedPreferences.getInstance();
    await prefs.setInt('last_sync_count', products.length);
    await prefs.setString('last_sync_time', DateTime.now().toIso8601String());
    print('Background sync: fetched ${products.length} products');
  } catch (e) {
    print('Background sync failed: $e');
  }
}

Step 2 — Initialise Workmanager in main()

lib/main.dart (inside main()) 
void main() async {
  // Required when calling native code before runApp()
  WidgetsFlutterBinding.ensureInitialized();

  // Initialise Workmanager and tell it where the callback lives
  await Workmanager().initialize(
    callbackDispatcher,  // the top-level function we wrote above
    isInDebugMode: false, // set to true during development to see logs
  );

  runApp( /* ... your MultiProvider + MaterialApp ... */ );
}

Step 3 — Register the task from the app

Call this from wherever it makes sense — for example, right after the user logs in, or when the app first opens.

// Register a PERIODIC task — runs roughly every 15 minutes
// (15 minutes is the minimum allowed by both Android and iOS)
await Workmanager().registerPeriodicTask(
  'product-sync-task',  // unique task ID — used to cancel it later
  'syncProducts',        // task name passed to callbackDispatcher
  frequency: const Duration(minutes: 15),
  constraints: Constraints(
    networkType: NetworkType.connected, // only run when online
    requiresBatteryNotLow: true,         // skip when battery is critical
  ),
  existingWorkPolicy: ExistingWorkPolicy.keep,
  // keep = if already scheduled, don't schedule again (prevents duplicates)
);

// Register a ONE-TIME task — runs once as soon as constraints are met
await Workmanager().registerOneOffTask(
  'cleanup-task',
  'dailyCleanup',
  initialDelay: const Duration(seconds: 10), // wait 10s before running
  constraints: Constraints(
    networkType: NetworkType.not_required,
    requiresCharging: true, // only run when plugged in
  ),
);

// Cancel a specific task by its unique ID
await Workmanager().cancelByUniqueName('product-sync-task');

// Cancel ALL registered tasks
await Workmanager().cancelAll();

8. The Constraints System

Constraints tell the OS the conditions under which your task is allowed to run. The OS will not run your task until all constraints are satisfied. This is how you make your app a good citizen — you tell the OS "only run my sync when the user is on WiFi and charging, so they don't pay for mobile data and don't lose battery."

Constraint Meaning Good for
networkType: connected Any internet connection (WiFi or mobile data) Quick API calls, sending logs
networkType: unmetered WiFi only (not mobile data) Large downloads, video sync, backup
networkType: not_required No internet required Local database cleanup, file compression
requiresBatteryNotLow: true Battery must not be critically low (<15%) Any background task — always good practice
requiresCharging: true Device must be plugged in Heavy work: full backup, ML processing, large uploads
requiresDeviceIdle: true Device must be idle (Android only) Non-urgent maintenance: database vacuuming, log rotation
requiresStorageNotLow: true Device storage must not be critically low Any task that writes files or data

9. Foreground Services — Long-Running User-Visible Work

A Foreground Service is a background service that the user is aware of. Unlike background tasks that run silently, a Foreground Service must display a persistent notification in the system notification bar as long as it is running. This is required by Android and is the iOS equivalent of a long-running background mode.

When is a Foreground Service required?

Use Case Why Foreground Service? App Example
Music playback Must keep playing after app is closed; user controls it from notification Spotify, YouTube Music
Turn-by-turn navigation Needs continuous GPS while user drives and switches apps Google Maps, Waze
Live workout tracking Records steps, heart rate, distance while user is active Strava, Nike Run Club
Active file download User triggered a large download; it must finish even if they switch apps Any download manager
Live location sharing Continuously sends GPS coordinates to a server for others to see WhatsApp Live Location, Uber driver app
VoIP call Must keep audio flowing even when the user locks the phone WhatsApp, Zoom, Teams

How a Foreground Service notification looks

┌──────────────────────────────────────────────────────────┐
│ 🎵 Spotify 9:41 AM │
│     Blinding Lights — The Weeknd │
│     [⏮] [⏸] [⏭] │
└──────────────────────────────────────────────────────────┘
     ↑ This notification stays in the tray as long as the service runs.
     The user can tap it to go back to the app, or interact with it directly.
The notification is not optional. Android will throw an exception if you start a Foreground Service without calling startForeground() with a notification within 5 seconds. On iOS, background modes like audio and location automatically show status bar indicators.

10. Which Background Approach to Use — Decision Guide

Is the work something the user is actively watching (music, navigation, call)?
→ YES → Foreground Service (with visible notification)
→ NO ↓

Does it need to happen exactly once and soon (upload a file after user taps send)?
→ YES → One-Time Task (workmanager.registerOneOffTask)
→ NO ↓

Should it repeat on a schedule (sync every 15 min, backup every day)?
→ YES → Periodic Task (workmanager.registerPeriodicTask)
→ NO ↓

Does the work only need to run while the app is in memory?
→ YES → Dart Isolate / compute() (see Lecture 17)
→ You probably don't need a background service at all

12. Common Mistakes to Avoid

❌ Accessing UI / Provider from background task

void callbackDispatcher() {
  Workmanager().executeTask((task, _) async {
    // ⚠️ CRASH — no BuildContext here
    final cart = context.read<CartProvider>();
    return Future.value(true);
  });
}

Background tasks run in a separate Isolate. There is no widget tree, no context, no Provider.

✅ Use only non-UI packages

void callbackDispatcher() {
  Workmanager().executeTask((task, _) async {
    // ✅ http and SharedPreferences work fine
    final prefs = await SharedPreferences.getInstance();
    final response = await http.get(...);
    await prefs.setString('last_sync', ...);
    return Future.value(true);
  });
}

Use packages that don't need Flutter: http, shared_preferences, sqflite.

❌ Registering the task inside build()

@override
Widget build(BuildContext context) {
  // ⚠️ called on every rebuild!
  Workmanager().registerPeriodicTask(...);
  return Scaffold(...);
}

Every rebuild schedules a new task. The OS ends up with dozens of duplicate tasks.

✅ Register once, use ExistingWorkPolicy.keep

// In initState() or after login — runs once
Workmanager().registerPeriodicTask(
  'sync-id',
  'syncProducts',
  existingWorkPolicy:
    ExistingWorkPolicy.keep, // ✅ skip if already registered
);

ExistingWorkPolicy.keep is your safety net — it ignores the call if the task is already scheduled.

❌ Expecting exact timing

// "Sync every 15 minutes exactly"
Workmanager().registerPeriodicTask(
  ...,
  frequency: Duration(minutes: 15),
);
// App syncs at: 10:00, 10:15, 10:30
// Reality: 10:00, 10:47, 12:03 ← OS delayed

The OS never guarantees exact timing. Battery optimization, Doze mode, and low power mode all cause delays.

✅ Design for approximate timing

// Store the last sync timestamp
await prefs.setString('last_sync',
  DateTime.now().toIso8601String());

// When app opens, check if data is stale
final lastSync = prefs.getString('last_sync');
if (dataIsStale(lastSync)) {
  await _loadProducts(); // pull fresh data
}

Check the timestamp when the user opens the app and refresh if the background task ran too long ago.

Key Takeaway: Background services let your app do useful work even when the user isn't looking — but the OS is firmly in control of when that work actually runs. Use Periodic Tasks for scheduled data sync, One-Time Tasks for deferred work triggered by the user, and Foreground Services for ongoing user-visible operations. Always use constraints to be a good battery citizen, always design for approximate timing (never exact), and remember that background code runs in a fresh Isolate — no UI, no Provider, no BuildContext.
