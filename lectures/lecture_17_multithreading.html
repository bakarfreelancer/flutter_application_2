1. What Is a Thread?

A thread is the smallest unit of execution that a CPU can run. Think of it as a worker who reads and executes instructions one by one.

  • A program can have one thread (single-threaded) or many threads (multi-threaded)
  • Multiple threads can run on multiple CPU cores truly at the same time (parallelism)
  • On a single core, threads take turns so fast it appears simultaneous (concurrency)
Single-threaded                      Multi-threaded

Worker 1: A → B → C → D → E      Worker 1: A → B → C
                                      Worker 2: D → E → F
Everything happens in order.      Tasks run in parallel.

In mobile development, one thread matters above all others: the UI thread (also called the main thread).

2. The UI Thread — The Most Important Thread

Every mobile operating system has a dedicated thread responsible for drawing the screen and handling user input. This is called the UI thread (or main thread).

The UI thread must draw a new frame 60 times per second (60 fps). That means it has only 16 milliseconds per frame. If any task on the UI thread takes longer than 16ms, the app skips frames — this is called jank, and the user sees it as stuttering or freezing.

60 fps = 1 frame every 16 milliseconds

Frame 1  [16ms] → Draw ✅
Frame 2  [16ms] → Draw ✅
Frame 3  [150ms — API call on UI thread!] → Late ❌ → User sees freeze
Frame 4  [16ms] → Draw ✅ (freeze over)

The golden rule of mobile development:

Never run slow work on the UI thread. Slow work includes: network requests, reading/writing files, heavy calculations, parsing large JSON, image processing. Always do this work on a background thread and only update the UI when the result is ready.

3. Two Kinds of Slow Work

Not all slow work is slow in the same way. Understanding the difference is critical:

I/O-bound work (waiting)

The CPU is not busy — it is just waiting for something external to respond.

  • Network request (waiting for the server)
  • Reading a file from disk
  • Querying a database

Solution: async / await
The thread is free while waiting — it can handle other things.

CPU-bound work (calculating)

The CPU is actively busy doing a calculation for a long time.

  • Parsing a 10 MB JSON file
  • Resizing or compressing an image
  • Encrypting a large file
  • Sorting a list of 100,000 items

Solution: Isolate / compute()
Must move to a truly separate thread — async alone is not enough.

4. Dart's Model — Single Thread + Event Loop

Dart (the language Flutter uses) is single-threaded. There is only one thread by default — and that thread runs both your code and the UI. So how does Dart handle slow I/O work without freezing?

Dart uses an Event Loop. The event loop sits and waits. Whenever a task finishes (e.g. a network response arrives), it adds the result to a queue. The event loop picks up the result and runs the code that was waiting for it.

Dart Event Loop

┌──────────────────────────────────────────────────┐
│            Event Queue                                │
│ [draw frame] [tap event] [API response arrived] │
└──────────────────────────────────────────────────┘
                   ↓ picks one at a time
┌──────────────────────────────────────────────────┐
│                Single Thread                      │
│       executes each task to completion       │
└──────────────────────────────────────────────────┘

The key insight: when Dart does an await on a network call, the thread is not sitting idle blocking. It registers a callback ("call me when the response arrives"), then goes back to the event loop to handle other events — like drawing the next frame or responding to a tap. When the response arrives, the callback is added to the queue and runs next.

Analogy: A waiter in a restaurant is single-threaded. He takes your order, walks to the kitchen and places it, then goes to serve other tables while the chef (the OS/hardware) does the slow cooking work. When the food is ready, he picks it up and brings it to you. He never stands at the kitchen window doing nothing. async/await is that waiter.

5. Future, async, and await — How They Work

Future

A Future<T> represents a value that does not exist yet but will exist at some point. It is a promise of a result.

// This function RETURNS IMMEDIATELY with a Future.
// The actual work (network call) happens later.
Future<String> fetchUsername() {
  return http.get(...).then((response) => response.body);
}

async / await — the readable way

async and await are just cleaner syntax for working with Futures. They make asynchronous code look like synchronous code.

// Without async/await — hard to read (callback style)
void loadUser() {
  fetchUsername().then((name) {
    print(name);
  });
}

// With async/await — reads top to bottom like normal code
Future<void> loadUser() async {
  final name = await fetchUsername(); // pause HERE until the Future completes
  print(name);                         // runs after the Future completes
}
await does NOT freeze the UI. When the code hits await, the current function pauses and gives control back to the event loop. The UI can still draw frames and respond to taps. The function resumes as soon as the awaited Future completes. This is what makes async I/O safe on the UI thread.

What the event loop actually does during an await

Time →

[UI Thread]   draw frame | handle tap | run _loadProducts() | ← await ← | resume after response | draw frame
                                                       ↕ free to draw frames while waiting
[OS/Network]                            ── network call in progress ──→ response ready → event queued

6. async/await in Our App — What We Already Built

We have been using async/await since Lecture 10 without thinking too deeply about it. Now we understand why it is the right tool for network calls.

// product_service.dart — I/O-bound work: waiting for the network
static Future<List<Product>> getProducts({...}) async {
  // await here: UI thread is FREE while the server responds.
  // Flutter can still draw frames — no jank.
  final response = await http.get(...);
  return productsJson.map((p) => Product.fromJson(p)).toList();
}

// home.dart — uses the result safely back on the UI thread
Future<void> _loadProducts() async {
  setState(() => _isLoading = true);
  final results = await ProductService.getProducts();
  setState(() {          // setState runs on the UI thread — correct
    _products = results;
    _isLoading = false;
  });
}

This is the correct pattern:

  1. Use await for the slow part (network) — UI stays responsive
  2. Call setState() after the await — updates the UI on the main thread

7. The Limit of async/await — CPU-Heavy Work

async/await solves waiting but not calculating. If you have a large, CPU-intensive task, even with async it will still block the UI thread because the Dart thread is actively running code, not waiting.

// This looks async but it STILL BLOCKS THE UI.
// There is no await — the for loop keeps the CPU busy on the UI thread.
Future<void> heavyWork() async {
  var sum = 0;
  for (var i = 0; i < 100000000; i++) { // 100 million iterations!
    sum += i;
  }
  print(sum);
}
Adding async to a function does NOT automatically run it in the background. It only means the function returns a Future and you can use await inside it. If the function never awaits anything, it runs entirely on the UI thread.

The solution for CPU-heavy work is a Dart Isolate.

8. Isolates — True Parallel Threads in Dart

A Dart Isolate is a fully separate thread with its own memory. Unlike regular threads in Java/C++ that share memory, Isolates are completely isolated — they cannot share variables. They communicate only by passing messages.

Regular thread (Java/Android)

  • Threads share memory
  • Risk of race conditions
  • Need locks / synchronized blocks
  • Complex and error-prone

Dart Isolate

  • Completely separate memory
  • No race conditions possible
  • Communicate via message passing
  • Safer and simpler
Isolates — Separate Memory

┌─────────────────────────┐   message   ┌─────────────────────────┐
│ Main Isolate (UI) │ ──────────→ │ Worker Isolate │
│ │ ←────────── │ │
│ Owns: _products, _skip │   result    │ Owns: copy of raw data │
│ Draws the UI │ │ Does heavy calculation │
└─────────────────────────┘ └─────────────────────────┘
                                No shared variables — data is copied

9. compute() — The Easy Way to Use Isolates

Creating and managing Isolates manually is verbose. Flutter provides a simpler helper function called compute() that handles all the setup automatically. You give it a function and some data — it runs the function in a background Isolate and returns the result as a Future.

import 'package:flutter/foundation.dart'; // compute() is here

// STEP 1: Write a TOP-LEVEL function (not inside a class)
// It must be a regular function — not async, not a method.
// This is the work that will run in the background Isolate.
List<Product> _parseProducts(String rawJson) {
  final data = jsonDecode(rawJson);
  final List list = data['products'];
  return list.map((p) => Product.fromJson(p)).toList();
  // This might take 200ms for a huge JSON — that's fine here,
  // because it runs on a background Isolate, not the UI thread.
}

// STEP 2: Call compute() — it spawns a background Isolate,
// runs _parseProducts(rawJson) there, and returns the result.
static Future<List<Product>> getProducts() async {
  final response = await http.get(...); // I/O-bound: fine with await

  // CPU-bound: parse the JSON in a background Isolate
  return await compute(_parseProducts, response.body);
  // ↑ first arg: the function to run
  // ↑ second arg: the data to send to it (copied, not shared)
}
Why a top-level function? Isolates have their own memory and cannot access the parent class's state. So the function must be defined outside any class — at the top level of the Dart file. This rule is enforced by the Dart VM.

10. When to Use What — Decision Guide

Situation Type of Work Solution
HTTP / network request I/O-bound (waiting) async / await
Reading / writing a file I/O-bound (waiting) async / await
Database query I/O-bound (waiting) async / await
Parsing a large JSON (> ~1 MB) CPU-bound (calculating) compute()
Resizing / compressing an image CPU-bound (calculating) compute()
Encrypting / hashing a large file CPU-bound (calculating) compute()
Sorting 100,000+ items CPU-bound (calculating) compute()
Parsing a small JSON (a few KB) CPU-bound but fast Fine on UI thread — no action needed
Quick Decision Rule

Is the work slow? → NO → Run it normally on the UI thread
                 → YES
                      Is it waiting for something external? → YES → async/await
                      Is the CPU actively calculating?     → YES → compute()

11. How Other Platforms Handle This

Every mobile platform has the same problem (UI thread must stay free) and uses the same general approach (do slow work elsewhere). The names differ:

Platform UI Thread Name I/O Async Solution CPU Parallel Solution
Flutter / Dart Main Isolate async / await / Future Isolate / compute()
Android (Kotlin) Main Thread Coroutines (suspend / launch) Dispatchers.Default (thread pool)
iOS (Swift) Main Thread async / await (Swift 5.5+) Grand Central Dispatch (GCD) background queues
React Native (JS) JS Thread async / await / Promise Native modules on background threads
The concept is universal. Whether you work in Flutter, Android, iOS, or React Native, the same rules apply: keep the UI thread free, use async for I/O-bound work, and use a background thread/isolate for CPU-bound work.

12. Common Mistakes to Avoid

❌ Calling setState from a background Isolate

void _myIsolateWork() {
  // ... heavy calculation ...
  setState(() { ... }); // ⚠️ CRASH
}

setState() must run on the main thread. Calling it from a background isolate crashes the app.

✅ Return the result, then setState

final result =
  await compute(_myIsolateWork, data);
// Back on main thread now:
setState(() { _data = result; }); // ✅

compute() returns to the main thread automatically. Call setState() after the await.

❌ Thinking async = runs in background

Future<void> heavyWork() async {
  for (int i = 0; i < 100000000; i++) {
    result += i; // still blocks UI!
  }
}

async alone does NOT move CPU work to a background thread. The loop still runs on the UI thread.

✅ Use compute() for CPU-heavy tasks

// Top-level function:
int _sumNumbers(int limit) {
  var result = 0;
  for (int i = 0; i < limit; i++) result += i;
  return result;
}
// In your widget:
final sum = await compute(_sumNumbers, 100000000); ✅

Now the loop runs in a background Isolate — the UI stays smooth.

❌ Forgetting to show loading state

await loadData();
// If this takes 3 seconds,
// user sees a blank/frozen screen
// with no feedback.

Even when the UI thread is free (async), the user needs to know something is happening.

✅ Always show a loading indicator

setState(() => _isLoading = true);
await loadData();
setState(() => _isLoading = false);
// CircularProgressIndicator shown
// while waiting — good UX ✅

Keep the user informed. A spinning indicator prevents the app from feeling broken.

13. Quick Reference

Concept Meaning
Future<T> A promise of a value T that will arrive later
async Marks a function as asynchronous — it returns a Future and can use await
await Pause this function until the Future completes; the UI thread is still free
Jank Dropped frames causing stutter — happens when the UI thread is blocked for >16ms
I/O-bound work Slow because it waits (network, file, DB) — fix with async/await
CPU-bound work Slow because it calculates (JSON parse, image resize) — fix with compute()
Isolate A completely separate Dart thread with its own memory — true parallelism
compute(fn, data) Runs fn(data) in a background Isolate; returns a Future with the result
