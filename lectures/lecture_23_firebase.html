1. What is Firebase?

Firebase is Google's Backend-as-a-Service (BaaS) platform. It gives mobile apps a ready-made backend — authentication, databases, storage, analytics — without you having to build or host a server yourself.

Before Firebase

You need to: set up a server, write REST APIs, manage a database, handle user sessions, store passwords securely, keep it running 24/7.

With Firebase

Google handles all of that. You call signInWithEmailAndPassword() and Firebase does the rest — server, encryption, tokens, sessions.

2. Firebase Project Setup (Do This Once)

Before writing any code, you must create a Firebase project and link it to your app. This is a one-time setup process.

  1. Create a Firebase project
    Go to console.firebase.google.com → click Add project → enter a name → Finish.
  2. Register your Android app
    In the project console → click the Android icon → enter the package name: com.example.flutter_application_2 → click Register app.
  3. Download google-services.json
    Click Download google-services.json → place the file at android/app/google-services.json.
    This file is your app's identity card for Firebase. Never commit it to a public GitHub repository.
  4. Enable Email/Password Authentication
    Firebase console → Authentication → Sign-in method → Email/Password → Enable → Save.
  5. Create a Firestore database
    Firebase console → Firestore Database → Create database → choose Start in test mode → pick a region → Done.
The app will crash on startup with "No Firebase App '[DEFAULT]' has been created" if google-services.json is missing from android/app/. This is the most common Firebase setup mistake.

4. Initializing Firebase in main()

Firebase must be initialized before runApp(). This connects the SDK to your Firebase project using the config in google-services.json. 

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();

  // Connect the app to Firebase using google-services.json
  await Firebase.initializeApp();

  await NotificationService.instance.init();

  runApp( ... );
}

5. Firebase Authentication

How it Works

Your app Firebase servers ────────────────────────────────────────────────────── signInWithEmailAndPassword() │ └─────────────────────────────────────────────► Checks email + password Returns a secure token ◄─────────────────────────────────────────────┘ │ Firebase SDK stores token on device automatically (you never touch SharedPreferences for auth again) │ authStateChanges stream fires: User object (non-null) │ App rebuilds → user is logged in

Key Methods

MethodWhat it does
signInWithEmailAndPassword(email, password)Sign in an existing user
createUserWithEmailAndPassword(email, password)Register a new user
signOut()Sign out the current user
currentUserThe currently signed-in User object (or null)
authStateChanges()Stream<User?> — fires on every sign-in/sign-out

The authStateChanges Stream

This is the key concept of Firebase Auth. Instead of checking SharedPreferences on startup, you simply listen to a stream. Firebase fires an event automatically whenever the auth state changes. 

class AuthProvider extends ChangeNotifier {
  User? _firebaseUser;

  bool get isLoggedIn => _firebaseUser != null;
  String get email => _firebaseUser?.email ?? '';
  String get uid   => _firebaseUser?.uid   ?? '';

  AuthProvider() {
    // Listen once — Firebase calls back whenever sign-in state changes.
    // On app start: fires immediately with the cached user (or null).
    // On login:     fires with the User object.
    // On logout:    fires with null.
    FirebaseAuth.instance.authStateChanges().listen((user) {
      _firebaseUser = user;
      notifyListeners();
    });
  }

  Future<String?> login(String email, String password) async {
    try {
      await FirebaseAuth.instance.signInWithEmailAndPassword(
        email: email, password: password,
      );
      return null; // null = success
    } on FirebaseAuthException catch (e) {
      return e.message; // show this in a SnackBar
    }
  }

  Future<void> logout() => FirebaseAuth.instance.signOut();
}
uid (user ID) is a unique string Firebase assigns to every user automatically. It never changes, even if the user updates their email. Always use uid as the key when storing user data — never the email address.

6. Cloud Firestore

Data Model

Firestore is a NoSQL database. Data is organised in a hierarchy of three levels:

Firestore └── users (Collection — like a table) ├── uid_abc123 (Document — like a row, identified by uid) │ ├── name: "Alice" │ ├── contact: "+1 555 0100" │ ├── address: "123 Main St" │ └── updatedAt: Nov 1 2026 │ └── uid_def456 (Document — another user) ├── name: "Bob" └── ...

Comparison: Firestore vs SQLite

SQLite (Lecture 19)Cloud Firestore
LocationOn the device onlyGoogle's cloud servers
Access from other devicesNoYes — same data everywhere
Real-time syncNoYes (snapshots stream)
Works offlineAlwaysYes, with automatic sync on reconnect
Query languageSQLChained method calls

Writing to Firestore

// Write (or update) a document at: users/{uid}
await FirebaseFirestore.instance
    .collection('users')    // select the collection
    .doc(uid)               // select (or create) the document
    .set(
      {
        'name':      name,
        'contact':   contact,
        'address':   address,
        'updatedAt': FieldValue.serverTimestamp(),
      },
      SetOptions(merge: true), // merge: don't wipe fields we didn't include
    );

Reading from Firestore

// Read the document for this user
final doc = await FirebaseFirestore.instance
    .collection('users')
    .doc(uid)
    .get();

if (doc.exists) {
  final data = doc.data()!;          // Map<String, dynamic>
  final name = data['name'] as String;
}

7. Before vs After Firebase

BEFORE (Lectures 05–13) ───────────────────────────────────────────────────────── LoginScreen → AuthService.login() → reqres.in API → store token in SharedPreferences → AuthProvider.checkAuthStatus() on startup AFTER (Lecture 23) ───────────────────────────────────────────────────────── LoginScreen → AuthProvider.login() → Firebase Auth → Firebase stores token automatically → authStateChanges stream → AuthProvider rebuilds → no SharedPreferences needed for auth
Firebase Auth persists the signed-in user automatically across app restarts. The authStateChanges stream fires with the cached user on every app launch. You no longer need to read a token from SharedPreferences on startup.

8. Handling Firebase Errors

Firebase throws FirebaseAuthException with a code string when something goes wrong. You should convert these codes into friendly messages.

Error CodeWhen it happensFriendly message
user-not-foundEmail not registered"No account found with this email."
wrong-password / invalid-credentialBad password"Incorrect email or password."
email-already-in-useRegistering a taken email"An account already exists with this email."
weak-passwordPassword under 6 chars"Password must be at least 6 characters."
network-request-failedNo internet"No internet connection."
try {
  await FirebaseAuth.instance.signInWithEmailAndPassword(...);
} on FirebaseAuthException catch (e) {
  // e.code gives the error code string
  switch (e.code) {
    case 'user-not-found': return 'No account found.';
    case 'wrong-password': return 'Incorrect password.';
    default: return 'Something went wrong.';
  }
}

9. Firestore Security Rules (Important!)

When you created your Firestore database in test mode, it allows anyone to read and write any data. This is fine for development but must be changed before releasing an app. 

// Firestore Rules — Firebase console → Firestore → Rules

// TEST MODE (allows all reads/writes — development only)
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if request.time < timestamp.date(2025, 12, 31);
    }
  }
}

// PRODUCTION (users can only read/write their own document)
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null
                         && request.auth.uid == uid;
    }
  }
}
Never ship an app with test mode rules. Any person on the internet can read or delete all user data in your database.
