3. Step 1 — App Configuration

Before building a release, configure the app's identity and version. These values cannot be changed after the first upload without consequences.

3.1 Application ID (Package Name)

The application ID is the globally unique identifier for your app on the Play Store. Once published, it can never change. 

// android/app/build.gradle.kts
android {
    defaultConfig {
        applicationId = "com.yourname.shopapp"   // ← change from default
        // Format: reverse domain notation
        // Good: com.johnsmith.shopapp
        // Bad:  com.example.flutter_application_2  ← never ship with "example"
    }
}
Never submit an app with com.example as the application ID. Google will reject it. Change it to something like com.yourname.appname before the very first upload.

3.2 Version Number

Two values control the version. Both must increase with every new upload to the Play Store. 

# pubspec.yaml
version: 1.0.0+1
#        │     └── versionCode (integer, must increase each upload: 1, 2, 3, …)
#        └──────── versionName (shown to users: "1.0.0", "1.1.0", "2.0.0")

versionNameYes ("1.0.0")Can be any string1.0.0 → 1.0.1 → 1.1.0 → 2.0.0

4. Step 2 — App Icons

Android requires launcher icons in many resolutions. The easiest way is to use the flutter_launcher_icons package. 

# pubspec.yaml — add in dev_dependencies
dev_dependencies:
  flutter_launcher_icons: ^0.14.0

# Also add the configuration block at the bottom of pubspec.yaml
flutter_launcher_icons:
  android: "launcher_icon"
  image_path: "assets/images/logo.jpg"  # your 512×512 icon
  adaptive_icon_background: "#FF6F00"   # background colour for adaptive icons
  adaptive_icon_foreground: "assets/images/logo.jpg"
# Run the generator — creates all required icon sizes automatically
flutter pub run flutter_launcher_icons

5. Step 3 — App Signing (Critical)

Every Android app published to the Play Store must be digitally signed with a keystore. A keystore is a file containing a private key that proves the app came from you.

What is a keystore? ───────────────────────────────────────────────────────── A keystore is like a digital passport for your app. Google uses it to verify that future updates come from the same developer. If you LOSE your keystore and password: → You can NEVER update your existing app on the Play Store. → You must publish it as a brand-new app with a new package name. → All your reviews and download history are lost. ⚠️ BACK UP YOUR KEYSTORE IN AT LEAST 2 SAFE PLACES.

5.1 Generate a Keystore

# Run this command ONCE. Replace the values with your own details.
keytool -genkey -v \
  -keystore ~/my_app_keystore.jks \
  -storetype JKS \
  -keyalg RSA \
  -keysize 2048 \
  -validity 10000 \
  -alias my_key \
  -storepass YOUR_STORE_PASSWORD \
  -keypass YOUR_KEY_PASSWORD \
  -dname "CN=Your Name, OU=Dev, O=Your Company, L=City, S=State, C=US"

This creates a file my_app_keystore.jks in your home directory. Write down the passwords — you will need them for every release build.

5.2 Store Signing Credentials Securely

Create a file android/key.properties (add this path to .gitignore!): 

# android/key.properties — NEVER commit this file to git!
storePassword=YOUR_STORE_PASSWORD
keyPassword=YOUR_KEY_PASSWORD
keyAlias=my_key
storeFile=/Users/yourname/my_app_keystore.jks
Add android/key.properties and *.jks / *.keystore to your .gitignore immediately. If these files are pushed to a public GitHub repository, anyone can sign apps in your name.

5.3 Configure Gradle to Sign the Release Build

// android/app/build.gradle.kts — add signing config

import java.util.Properties
import java.io.FileInputStream

// Read key.properties
val keyPropertiesFile = rootProject.file("key.properties")
val keyProperties = Properties()
keyProperties.load(FileInputStream(keyPropertiesFile))

android {
    signingConfigs {
        create("release") {
            storeFile    = file(keyProperties["storeFile"] as String)
            storePassword = keyProperties["storePassword"] as String
            keyAlias     = keyProperties["keyAlias"] as String
            keyPassword  = keyProperties["keyPassword"] as String
        }
    }

    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")  // ← use our key
            isMinifyEnabled = true    // shrink code size
            isShrinkResources = true  // remove unused resources
        }
    }
}

6. Step 4 — Building the Release

APK vs AAB — Which to Use?

APK (Android Package)AAB (Android App Bundle)
Play Store uploadAccepted (legacy)Required since Aug 2021
Direct installationYes (sideloading)No — must go through Play Store
File size delivered to userFull sizeSmaller (only device-relevant resources)
Use caseTesting, sideloading, enterprisePlay Store publication

Build Commands

# Build release AAB — for Play Store upload (REQUIRED)
flutter build appbundle --release
# Output: build/app/outputs/bundle/release/app-release.aab

# Build release APK — for direct testing or sideloading
flutter build apk --release
# Output: build/app/outputs/apk/release/app-release.apk

# Build split APKs (smaller files, one per CPU architecture)
flutter build apk --split-per-abi
# Outputs: app-armeabi-v7a-release.apk, app-arm64-v8a-release.apk, app-x86_64-release.apk
Before building for release, always run flutter clean first to remove any cached debug build artifacts. A dirty build cache can cause signing errors. 
# Clean build cache first, then build
flutter clean
flutter pub get
flutter build appbundle --release

7. Step 5 — Google Play Console Setup

  • 1
    Create a new app
    Play Console → All apps → Create app. Choose: App or Game, Free or Paid, confirm policies.
  • 2
    Fill in the store listing
    Store presence → Main store listing.
    Add: App name, short description, full description, icon (512×512 PNG), feature graphic (1024×500 PNG), and at least 2 phone screenshots.
  • 3
    Complete the content rating questionnaire
    Policy → App content → Content rating.
    Answer questions honestly. The rating is assigned automatically.
  • 4
    Set up target audience
    Policy → App content → Target audience and content.
    Choose "18 and over" for apps with no specific child focus.
  • 5
    Add a privacy policy
    Policy → App content → Privacy policy.
    Required if your app uses Firebase, location, camera, or contacts.
  • 6
    Set up pricing and distribution
    Monetise → Pricing and distribution (legacy UI) or Store presence → Countries and regions.
    Choose Free or Paid, select which countries to publish to.

8. Step 6 — Uploading the AAB

Play Console uses tracks to control who receives your app. Always test on Internal or Alpha before going to Production.

RELEASE TRACKS (in order of testing confidence) ───────────────────────────────────────────────────────────────────── Internal testing → up to 100 testers you add by email → no review needed, published in minutes → use this FIRST to verify signing works Closed testing → up to 2000 testers (Alpha / Beta tracks) (Alpha / Beta) → testers must opt in via a link → quick review by Google Open testing → anyone can join (Production-like) → full Google review required Production → live on the Play Store for everyone → full Google review (1–3 business days)

Upload Steps

  • 1
    Go to Testing → Internal testing → Create new release.
  • 2
    Click Upload → select app-release.aab from build/app/outputs/bundle/release/.
  • 3
    Add release notes (what's new in this version) → Save → Review release → Start rollout.
  • 4
    Once internal testing looks good, go to Production → Create new release → upload the same AAB → roll out to Production.

9. Pre-Release Checklist

Go through every item before uploading to Production:

  • Application ID changed from com.example.* to your own domain
  • versionCode incremented from the previous upload
  • versionName updated to reflect the new release
  • Keystore backed up in at least 2 locations (cloud + USB drive)
  • key.properties is in .gitignore and never committed to git
  • App tested on a real device or emulator in release mode
  • All debug-only code removed (test credentials, log statements, banners)
  • debugShowCheckedModeBanner: false in MaterialApp (already done)
  • Permissions in AndroidManifest match only what the app actually uses
  • App icon generated and shows correctly on the home screen
  • Store listing screenshots taken (minimum 2)
  • Privacy policy URL live and accessible
  • Content rating questionnaire completed
  • Google Play Developer account active (≥ 24–48 hrs after registration)
