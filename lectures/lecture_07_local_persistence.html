1. What is Local Data Persistence?

When an app closes, everything in memory (variables, state) is lost. Local data persistence means saving data on the device so it survives app restarts.

Storage TypeBest ForExample
SharedPreferencesSmall key-value dataUser name, settings, dark mode toggle
SQLite / HiveStructured / large dataProducts list, order history
File storageFiles, images, documentsDownloaded PDFs

In this lecture we use SharedPreferences — the simplest option, perfect for saving a small number of values like user profile info.

2. How SharedPreferences Works

SharedPreferences stores data as key-value pairs — like a dictionary. You give each piece of data a unique key (a string), and you can save or retrieve it using that key.

SharedPreferences (stored on device)

┌──────────────┬───────────────────┐
│ Key │ Value │
├──────────────┼───────────────────┤
│ "user_name" │ "Ali Hassan" │
│ "user_contact"│ "0300-1234567" │
│ "user_address"│ "Street 5, LHR" │
└──────────────┴───────────────────┘

Basic operations

// Get instance
final prefs = await SharedPreferences.getInstance();

// Save a string
await prefs.setString('user_name', 'Ali Hassan');

// Read a string (returns null if key does not exist)
final name = prefs.getString('user_name');

// Delete a value
await prefs.remove('user_name');
await? SharedPreferences reads from the device disk — this takes a tiny amount of time. We use await to wait for it to finish before continuing. Any function that uses await must be marked async.

3. Adding the Package

SharedPreferences is not built into Flutter — we add it as a dependency.

Step 1 — add to pubspec.yaml:

dependencies:
  flutter:
    sdk: flutter
  cupertino_icons: ^1.0.8
  shared_preferences: ^2.3.0   ← add this line

Step 2 — run in terminal:

flutter pub get

Step 3 — import in Dart files where you need it:

import 'package:shared_preferences/shared_preferences.dart';

5. UserStorage — The Helper Class

Instead of writing SharedPreferences code in every screen, we create one service class that handles all storage operations. Screens just call its methods — they don't need to know how storage works.

lib/services/user_storage.dart 
import 'package:shared_preferences/shared_preferences.dart';

class UserStorage {
  // Constants for keys — prevents typos when reading/writing
  static const String _keyName    = 'user_name';
  static const String _keyContact = 'user_contact';
  static const String _keyAddress = 'user_address';

  // Save all three fields at once
  static Future<void> saveUser({
    required String name,
    required String contact,
    required String address,
  }) async {
    final prefs = await SharedPreferences.getInstance();
    await prefs.setString(_keyName, name);
    await prefs.setString(_keyContact, contact);
    await prefs.setString(_keyAddress, address);
  }

  // Read all three fields, return as a Map
  static Future<Map<String, String>> getUser() async {
    final prefs = await SharedPreferences.getInstance();
    return {
      'name':    prefs.getString(_keyName)    ?? '',
      'contact': prefs.getString(_keyContact) ?? '',
      'address': prefs.getString(_keyAddress) ?? '',
    };
  }

  // Returns true if user data already exists
  static Future<bool> hasUser() async {
    final prefs = await SharedPreferences.getInstance();
    final name = prefs.getString(_keyName) ?? '';
    return name.isNotEmpty;
  }
}
Why static methods? We mark the methods static so we can call them without creating an object — UserStorage.hasUser() instead of UserStorage().hasUser(). This is a common pattern for utility/service classes.

6. UserInfoScreen — First-Launch Form

This screen is shown only once — the first time the app opens. It collects the user's name, contact, and address, saves them, then navigates to the home screen.

lib/screens/user_info_screen.dart — key parts 
class _UserInfoScreenState extends State<UserInfoScreen> {
  final TextEditingController _nameController    = TextEditingController();
  final TextEditingController _contactController = TextEditingController();
  final TextEditingController _addressController  = TextEditingController();

  Future<void> _saveAndContinue() async {
    // 1. Validate — all fields must be filled
    if (_nameController.text.isEmpty || ...) {
      ScaffoldMessenger.of(context).showSnackBar(...);
      return;
    }

    // 2. Save to local storage via UserStorage
    await UserStorage.saveUser(
      name:    _nameController.text,
      contact: _contactController.text,
      address: _addressController.text,
    );

    // 3. Navigate to home — pushReplacement so user cannot go back
    Navigator.pushReplacement(
      context,
      MaterialPageRoute(builder: (_) => const MyApp()),
    );
  }
}
Why pushReplacement? We use pushReplacement instead of push so the user cannot press the back button to return to the info form after saving. The form is a one-time screen.

7. Conditional Navigation in Splash Screen

The Splash screen is now responsible for deciding where to send the user. After the 2-second delay, it checks UserStorage.hasUser() and navigates accordingly.

lib/screens/splash.dart 
class _SplashScreenState extends State<SplashScreen> {
  @override
  void initState() {
    super.initState();
    _navigate(); // call our async method
  }

  Future<void> _navigate() async {
    // Wait 2 seconds for the splash to show
    await Future.delayed(const Duration(seconds: 2));

    if (!mounted) return; // safety check

    // Check if user data exists in storage
    final userExists = await UserStorage.hasUser();

    if (!mounted) return; // safety check after await

    Navigator.pushReplacement(
      context,
      MaterialPageRoute(
        builder: (_) => userExists
            ? const MyApp()            // data found → go to home
            : const UserInfoScreen(),  // no data → show form
      ),
    );
  }
}

Why do we check mounted twice?

After an await, the widget might have been removed from the screen (e.g. user closed the app). Calling Navigator on an unmounted widget causes an error. The if (!mounted) return check prevents this.

8. Profile Screen — Reading & Displaying Data

The Profile tab reads the saved data in initState and displays it.

lib/screens/profile.dart — key parts 
class _ProfileScreenState extends State<ProfileScreen> {
  String name = '';
  String contact = '';
  String address = '';

  @override
  void initState() {
    super.initState();
    _loadUser(); // load data when the screen is created
  }

  Future<void> _loadUser() async {
    final data = await UserStorage.getUser();
    setState(() {           // setState to rebuild UI with the loaded data
      name    = data['name']!;
      contact = data['contact']!;
      address = data['address']!;
    });
  }
}

9. async / await — Quick Reference

KeywordMeaning
asyncMarks a function as asynchronous — it can use await inside
awaitPause here until this operation finishes, then continue
Future<void>Return type for an async function that returns nothing
Future<bool>Return type for an async function that eventually returns a bool
// Without async/await — wrong, result not ready yet
final name = SharedPreferences.getInstance().getString('user_name'); // ❌

// With async/await — correct
final prefs = await SharedPreferences.getInstance();
final name  = prefs.getString('user_name'); // ✅
