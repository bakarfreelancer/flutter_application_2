1. The Problem — Loading Everything at Once

Our home screen currently fetches all 20 products in one go and displays them. Two problems exist:

  1. No refresh: If the product catalogue changes, the only way to see the update is to restart the app.
  2. Poor performance at scale: Loading 20 items is fine, but real apps have thousands of products. Loading them all at once is slow and wastes memory.

The industry solution is pagination — load a small batch (e.g. 10 items), and when the user scrolls to the bottom, load the next batch. Combined with pull-to-refresh, the app feels live and responsive.

Before: load all 20 at once, no way to refresh

App starts → fetch 20 products → show them → done ❌

After: load 10 at a time, pull-down to reload

App starts → fetch products 1-10 → show them
User scrolls down → fetch products 11-20 → append
User scrolls down → fetch products 21-30 → append ...
User pulls down → reload from product 1 ✅

2. How API Pagination Works — limit & skip

The dummyjson.com API supports two query parameters for pagination:

Parameter Meaning Example
limit How many items to return limit=10 → return 10 items
skip How many items to skip from the start skip=20 → skip the first 20, start from item 21

By combining them you can request any page:

Page URL Items returned
Page 1 /products?limit=10&skip=0 Items 1 – 10
Page 2 /products?limit=10&skip=10 Items 11 – 20
Page 3 /products?limit=10&skip=20 Items 21 – 30
Last page (6 items left) /products?limit=10&skip=90 Items 91 – 96 (only 6)
How do we know we've reached the last page? When the API returns fewer items than our limit, there is no next page. If we asked for 10 but got 6, we're done. We track this with a _hasMore flag.

3. The State Variables We Need

Unlike the old FutureBuilder approach (one future, Flutter handles states), we are now managing the state ourselves. We need five variables:

Variable Type Purpose
_products List<Product> All products loaded so far (grows as pages are added)
_skip int How many products to skip for the next API call
_isLoading bool True while the first page loads (shows full-screen spinner)
_isLoadingMore bool True while a subsequent page loads (shows spinner at bottom)
_hasMore bool False when the API returned fewer items than _pageSize — no more pages
Why two loading flags? _isLoading is for the very first load — we show a full-screen spinner and nothing else. _isLoadingMore is for subsequent pages — we keep the existing products visible and just add a small spinner at the bottom of the list.

5. Step 1 — Update ProductService

A small but important change: add limit and skip named parameters to getProducts() with sensible defaults.

lib/services/product_service.dart 
// Before (Lecture 10):
// static Future<List<Product>> getProducts() async {
//   final response = await http.get(Uri.parse('$_baseUrl/products?limit=20'));

// After (Lecture 15): named parameters with default values
static Future<List<Product>> getProducts({
  int limit = 10,
  int skip  = 0,
}) async {
  final response = await http.get(
    Uri.parse('$_baseUrl/products?limit=$limit&skip=$skip'),
  );

  if (response.statusCode == 200) {
    final data = jsonDecode(response.body);
    final List productsJson = data['products'];
    return productsJson.map((p) => Product.fromJson(p)).toList();
  }

  throw Exception('Failed to load products');
}
Named parameters with defaults: Because we used {int limit = 10, int skip = 0}, existing code that calls ProductService.getProducts() with no arguments still works — it just gets the first 10 items. We only pass explicit values when we want a specific page.

6. Step 2 — Rewrite _HomeContent State

We replace the single Future with the five state variables and a ScrollController. The controller is created once and cleaned up in dispose().

lib/screens/home.dart — state variables & lifecycle 
class _HomeContentState extends State<_HomeContent> {

  // Products loaded so far — grows as pages are appended
  final List<Product> _products = [];

  static const int _pageSize = 10; // items per page
  int  _skip          = 0;     // how many to skip for the next fetch
  bool _isLoading     = true;  // first load in progress
  bool _isLoadingMore = false; // next page in progress
  bool _hasMore       = true;  // false when no more pages exist
  String? _error;              // non-null if the first load failed

  // ScrollController — we attach this to ListView to detect scroll position
  final ScrollController _scrollController = ScrollController();

  @override
  void initState() {
    super.initState();
    _loadProducts();                        // fetch page 1
    _scrollController.addListener(_onScroll); // watch for scroll events
  }

  @override
  void dispose() {
    _scrollController.dispose(); // always clean up controllers!
    super.dispose();
  }
}
Always call dispose()! If you create a ScrollController (or TextEditingController, AnimationController, etc.) you must call .dispose() when the widget is removed from the tree. Forgetting causes memory leaks — the controller keeps listening to scroll events forever, even after the screen is gone.

7. Step 3 — The Scroll Listener

The scroll listener is called every time the user moves their finger on the list. We check: are we near the bottom, not already loading, and is there more data? If all three are true, we load the next page.

lib/screens/home.dart — _onScroll 
void _onScroll() {
  // pixels        = how far the user has scrolled (from the top)
  // maxScrollExtent = the total scrollable distance of the list
  //
  // When pixels == maxScrollExtent the user is at the very bottom.
  // We subtract 200 to trigger loading a little BEFORE they hit the end,
  // so the next page appears seamlessly without a blank gap.
  final atBottom =
      _scrollController.position.pixels >=
      _scrollController.position.maxScrollExtent - 200;

  if (atBottom && !_isLoadingMore && _hasMore) {
    _loadMore();
  }
}

8. Step 4 — The Two Loading Functions

We split loading into two separate functions so the logic stays clear:

_loadProducts() — first load & pull-to-refresh

lib/screens/home.dart — _loadProducts 
// Called on app start AND when the user pulls down to refresh.
// Always resets back to page 1.
Future<void> _loadProducts() async {
  setState(() {
    _isLoading = true;
    _error     = null;
  });

  try {
    final results = await ProductService.getProducts(
      limit: _pageSize,
      skip: 0, // always start from the beginning
    );

    setState(() {
      _products.clear();         // throw away old products
      _products.addAll(results); // put in the fresh first page
      _skip    = results.length;  // next fetch will skip past these
      _hasMore = results.length == _pageSize; // fewer = last page
      _isLoading = false;
    });
  } catch (e) {
    setState(() {
      _error     = e.toString();
      _isLoading = false;
    });
  }
}

_loadMore() — next page

lib/screens/home.dart — _loadMore 
// Called when the user scrolls near the bottom.
// APPENDS the next page — does NOT clear the existing list.
Future<void> _loadMore() async {
  setState(() => _isLoadingMore = true);

  try {
    final results = await ProductService.getProducts(
      limit: _pageSize,
      skip: _skip, // skip past everything already shown
    );

    setState(() {
      _products.addAll(results); // APPEND — don't clear!
      _skip    += results.length;  // advance the pointer
      _hasMore  = results.length == _pageSize;
      _isLoadingMore = false;
    });
  } catch (_) {
    // Pagination failure: just hide the spinner, let user try again by scrolling
    setState(() => _isLoadingMore = false);
  }
}
The key difference: _loadProducts() calls _products.clear() before adding. _loadMore() only calls _products.addAll(). Never clear in _loadMore() — the user would see all existing products disappear while waiting.

9. Step 5 — The Build Method

The build method handles three states and wraps the list in RefreshIndicator.

lib/screens/home.dart — build() 
@override
Widget build(BuildContext context) {

  // State 1: first load still in progress
  if (_isLoading) {
    return const Center(child: CircularProgressIndicator());
  }

  // State 2: first load failed — show error + retry button
  if (_error != null) {
    return Center(
      child: Column(
        mainAxisAlignment: MainAxisAlignment.center,
        children: [
          const Icon(Icons.wifi_off, size: 48, color: Colors.grey),
          const SizedBox(height: 12),
          const Text('Something went wrong'),
          const SizedBox(height: 16),
          ElevatedButton(
            onPressed: _loadProducts, // retry
            child: const Text('Try Again'),
          ),
        ],
      ),
    );
  }

  // State 3: data loaded — wrap ListView in RefreshIndicator
  return RefreshIndicator(
    // onRefresh is called when the user pulls down from the top.
    // It must return a Future — we pass _loadProducts directly.
    onRefresh: _loadProducts,

    child: ListView.builder(
      controller: _scrollController, // connect our scroll listener
      padding: const EdgeInsets.all(12),

      // +1 for the loading spinner at the bottom (shown while _isLoadingMore is true
      // or while there are still more pages to load)
      itemCount: _products.length + (_isLoadingMore || _hasMore ? 1 : 0),

      itemBuilder: (context, index) {
        // Last item = the spinner row
        if (index == _products.length) {
          return const Padding(
            padding: EdgeInsets.symmetric(vertical: 24),
            child: Center(child: CircularProgressIndicator()),
          );
        }
        // All other items = product cards
        return _ProductCard(product: _products[index]);
      },
    ),
  );
}
RefreshIndicator is just a wrapper. You wrap your existing ListView with it and provide an onRefresh callback. Flutter handles the spinning animation, the overscroll physics, and calling your callback automatically.

10. The Complete Flow

App Opens
→ initState() → _loadProducts() → sets _isLoading=true
→ API call: /products?limit=10&skip=0
→ response arrives → _products = [1..10], _skip=10, _isLoading=false
→ ListView shows products 1-10 ✅

User Scrolls Near Bottom
→ _onScroll() detects position → calls _loadMore()
→ sets _isLoadingMore=true → spinner appears at bottom
→ API call: /products?limit=10&skip=10
→ response: _products.addAll([11..20]), _skip=20
→ _isLoadingMore=false → spinner gone, 20 products shown ✅

User Pulls Down from Top
→ RefreshIndicator.onRefresh → calls _loadProducts()
→ _products.clear() → API: /products?limit=10&skip=0
→ fresh data replaces everything ✅

Last Page Reached
→ API returns 6 items (less than limit=10)
→ _hasMore = false → scroll listener stops calling _loadMore()
→ no spinner at bottom → end of list ✅

11. Common Mistakes to Avoid

❌ Clearing the list in _loadMore

Future<void> _loadMore() async {
  final results = await ...;
  setState(() {
    _products.clear();    // ⚠️ wrong!
    _products.addAll(results);
  });
}

All existing products vanish while loading. The user sees a blank screen.

✅ Only append in _loadMore

Future<void> _loadMore() async {
  final results = await ...;
  setState(() {
    // No clear() here!
    _products.addAll(results); // ✅
  });
}

Existing products stay visible. New ones appear at the bottom.

❌ No guard against duplicate fetches

void _onScroll() {
  if (atBottom) {
    _loadMore(); // called many times
  }             // while already loading!
}

The user gets duplicate products because the same page is fetched multiple times.

✅ Check _isLoadingMore before fetching

void _onScroll() {
  if (atBottom
      && !_isLoadingMore  // ✅ guard
      && _hasMore) {
    _loadMore();
  }
}

The flag prevents any duplicate calls while a fetch is already running.

❌ Forgetting dispose()

// No dispose override
// ScrollController keeps
// listening forever!

Memory leak — the controller survives even after the widget is gone.

✅ Always dispose controllers

@override
void dispose() {
  _scrollController.dispose(); // ✅
  super.dispose();
}

Resources are freed as soon as the widget leaves the screen.

Key Takeaway: Pagination and pull-to-refresh are two of the most common patterns in real mobile apps. The core idea is simple — limit and skip control which page of data you request, addAll() vs clear() decides whether you replace or extend the list, and ScrollController tells you when to fetch the next page. RefreshIndicator handles the pull gesture with just one wrapper widget.
