1. The Problem — Hardcoded Colors

Our app is fully working, but if you look at the code you will find Colors.orangeAccent written in many different files:

  • top_header.dart — header background and icon colors
  • bottom_nav_bar.dart — selected tab color

2. Key Concepts Before We Code

ThemeData

ThemeData is a Flutter class that holds all the visual settings for your app — colors, font sizes, button shapes, etc. You define it once in MaterialApp and it applies to every widget in the entire app.

ColorScheme

ColorScheme is a set of coordinated colors inside ThemeData. You give it one seed color (your brand color) and Flutter automatically generates all the other colors — primary, secondary, background, surface, etc. — that look good together.

ColorScheme Property What It's Used For Light Example Dark Example
primary Main brand color — buttons, active icons, headers Deep orange Light orange
onPrimary Color that looks good ON TOP of primary White Dark brown
surface Card and dialog backgrounds White Dark grey
onSurface Text on cards/dialogs Black White
Rule of thumb: If you want to place text or an icon on top of a color, use the matching on variant. Example: text on a primary-colored header → use colorScheme.onPrimary.

Theme.of(context)

Any widget can call Theme.of(context) to get the current theme. From there you can read any color: Theme.of(context).colorScheme.primary

ThemeMode

Flutter's MaterialApp has a themeMode property that accepts:

  • ThemeMode.light — always use the light theme
  • ThemeMode.dark — always use the dark theme
  • ThemeMode.system — follow the phone's system setting

4. Step 1 — Create ThemeProvider

Just like CartProvider manages cart items and AuthProvider manages login state, ThemeProvider manages whether the app is in dark or light mode. It uses the same ChangeNotifier pattern you already know.

lib/providers/theme_provider.dart (new file) 
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';

class ThemeProvider extends ChangeNotifier {
  bool _isDark = false;

  // Public getter — any widget can read this
  bool get isDark => _isDark;

  // ThemeMode.light or ThemeMode.dark — used by MaterialApp
  ThemeMode get themeMode => _isDark ? ThemeMode.dark : ThemeMode.light;

  // Constructor — runs as soon as the provider is created at app start.
  // This loads the saved preference so the theme is restored immediately.
  ThemeProvider() {
    _loadTheme();
  }

  // Read the saved value from SharedPreferences
  Future<void> _loadTheme() async {
    final prefs = await SharedPreferences.getInstance();
    _isDark = prefs.getBool('is_dark') ?? false; // default: light mode
    notifyListeners();
  }

  // Called when the user flips the switch in the Profile screen
  Future<void> toggleTheme() async {
    _isDark = !_isDark; // flip the value
    final prefs = await SharedPreferences.getInstance();
    await prefs.setBool('is_dark', _isDark); // save to local storage
    notifyListeners(); // 🔔 tell all widgets: rebuild with the new theme
  }
}
You already know this pattern! The ThemeProvider is structurally identical to AuthProvider from Lecture 13 — a private variable, a public getter, and methods that change the variable and call notifyListeners(). The only new thing is ThemeMode.

5. Step 2 — Update main.dart

Three things to add here:

  1. Register ThemeProvider in MultiProvider
  2. Define a theme (light) and darkTheme using ThemeData
  3. Wrap MaterialApp in a Consumer<ThemeProvider> so it rebuilds when the theme changes
lib/main.dart 
import 'package:flutter/material.dart';
import 'package:provider/provider.dart';
import 'package:flutter_application_2/providers/cart_provider.dart';
import 'package:flutter_application_2/providers/auth_provider.dart';
import 'package:flutter_application_2/providers/theme_provider.dart'; // NEW
import 'package:flutter_application_2/screens/splash.dart';

void main() {
  runApp(
    MultiProvider(
      providers: [
        ChangeNotifierProvider(create: (_) => CartProvider()),
        ChangeNotifierProvider(create: (_) => AuthProvider()),
        ChangeNotifierProvider(create: (_) => ThemeProvider()), // NEW
      ],

      // Consumer listens to ThemeProvider. When toggleTheme() is called,
      // this Consumer rebuilds — which rebuilds MaterialApp with the new themeMode.
      child: Consumer<ThemeProvider>(
        builder: (context, themeProvider, child) {
          return MaterialApp(
            title: 'My App',
            debugShowCheckedModeBanner: false,

            // Which theme to show right now — light or dark
            themeMode: themeProvider.themeMode, // NEW

            // Light theme — used when isDark is false
            theme: ThemeData(
              colorScheme: ColorScheme.fromSeed(
                seedColor: Colors.orange, // our brand color
              ),
              useMaterial3: true,
            ),

            // Dark theme — used when isDark is true
            // Same seed color, but brightness: Brightness.dark tells
            // Flutter to generate dark background colors automatically.
            darkTheme: ThemeData(
              colorScheme: ColorScheme.fromSeed(
                seedColor: Colors.orange,
                brightness: Brightness.dark, // NEW — makes Flutter generate dark colors
              ),
              useMaterial3: true,
            ),

            home: const SplashScreen(),
          );
        },
      ),
    ),
  );
}
Why Consumer here? MaterialApp is the root of the widget tree. When themeMode changes, we need the whole tree to rebuild with the new theme. Wrapping MaterialApp in a Consumer<ThemeProvider> makes exactly that happen — the moment toggleTheme() is called, the consumer rebuilds MaterialApp with the new themeMode.

6. Step 3 — Fix home.dart (Important!)

Before this lecture, the MyApp widget in home.dart returned its own MaterialApp — a widget inside a widget. This created two MaterialApps in the tree, and the inner one had no theme defined, so our theme from main.dart would not apply to the home screens.

The fix is simple: remove the inner MaterialApp and just return a Scaffold directly. The outer MaterialApp in main.dart is already wrapping everything.

The inner MaterialApp has no theme, so our custom colors are ignored.

✅ After — one MaterialApp in main.dart

Now the theme from main.dart flows all the way down to every widget.

9. Step 6 — Update ProfileScreen + Add Dark Mode Toggle

Two things to do in the profile screen:

  1. Replace hardcoded colors with theme colors (avatar, info tile icons)
  2. Add a dark mode toggle Switch widget
lib/screens/profile.dart (key parts) 
// 1. Read both providers at the top of build()
final themeProvider = context.watch<ThemeProvider>();
final primaryColor  = Theme.of(context).colorScheme.primary;

// 2. Avatar now uses theme colors
CircleAvatar(
  backgroundColor: primaryColor,    // was: Colors.orangeAccent
  child: Text(
    ...,
    style: TextStyle(
      color: Theme.of(context).colorScheme.onPrimary, // was: Colors.white
    ),
  ),
),

// 3. Dark mode toggle — add this row in the Column
Row(
  mainAxisAlignment: MainAxisAlignment.spaceBetween,
  children: [
    Row(
      children: [
        Icon(
          // Show different icon based on current mode
          themeProvider.isDark ? Icons.dark_mode : Icons.light_mode,
          color: primaryColor,
        ),
        const SizedBox(width: 12),
        const Text('Dark Mode', style: TextStyle(fontSize: 16)),
      ],
    ),
    // Switch reads isDark and calls toggleTheme() when the user flips it
    Switch(
      value: themeProvider.isDark,
      onChanged: (_) => context.read<ThemeProvider>().toggleTheme(),
      activeThumbColor: primaryColor,
    ),
  ],
),
Why context.read inside onChanged? We use context.watch at the top of build() to listen for changes (so the icon updates). We use context.read inside the callback to call a method without subscribing. This is the same pattern from Lecture 12.

10. How It All Works Together

User flips the Switch in ProfileScreen
↓
context.read<ThemeProvider>().toggleTheme()
↓
_isDark flips · saved to SharedPreferences · notifyListeners()
↓
Consumer<ThemeProvider> in main.dart rebuilds
↓
MaterialApp gets new themeMode (light ↔ dark)
↓
Every widget that uses Theme.of(context) gets new colors ✅

Next app restart → ThemeProvider constructor calls _loadTheme()
→ reads saved is_dark from SharedPreferences → restores the right theme ✅

What You Want to Do Code

Get the color to put ON the primary color Theme.of(context).colorScheme.onPrimary

12. Common Mistakes to Avoid

❌ Two MaterialApps in the tree

// main.dart
MaterialApp(theme: myTheme, ...)

// home.dart — another one!
MaterialApp(home: Scaffold(...))

The inner MaterialApp blocks the outer theme. Widgets inside it will never see your ThemeData.

✅ One MaterialApp, return Scaffold

// main.dart
MaterialApp(theme: myTheme, ...)

// home.dart — plain Scaffold
Scaffold(
  appBar: ..., body: ...,
)

The theme flows down to every widget in the tree.

❌ Calling toggleTheme with watch

Switch(
  onChanged: (_) =>
    context.watch<ThemeProvider>()
           .toggleTheme(), // ⚠️
)

context.watch is for reading in build(). Using it inside callbacks causes issues.

✅ Use read inside callbacks

Switch(
  onChanged: (_) =>
    context.read<ThemeProvider>()
           .toggleTheme(), // ✅
)

context.read is for calling methods. context.watch is for reading state in build().

❌ Forgetting Consumer in main.dart

// Without Consumer:
MaterialApp(
  themeMode: ThemeMode.light, // hardcoded!
  ...
)

MaterialApp never rebuilds — flipping the switch does nothing visible.

✅ Wrap MaterialApp in Consumer

Consumer<ThemeProvider>(
  builder: (_, tp, __) => MaterialApp(
    themeMode: tp.themeMode, // reactive!
    ...
  ),
)

Now MaterialApp rebuilds whenever ThemeProvider calls notifyListeners().

Key Takeaway: Theming is about separation of concerns — define your colors once in ThemeData, then read them everywhere with Theme.of(context). The dark mode toggle combines three things you already know: Provider (Lecture 12) to manage state, SharedPreferences (Lecture 7) to save the choice, and Consumer (Lecture 12) to trigger a rebuild of MaterialApp. No new Flutter APIs were needed — just existing knowledge applied to a new problem.
