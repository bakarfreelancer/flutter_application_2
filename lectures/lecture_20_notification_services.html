1. What Is a Notification?

A notification is a short message that appears outside the app — in the status bar, on the lock screen, or as a banner at the top of the screen — to inform the user about something important.

🛍
ShopApp
Your order has been placed! Tap to track.
now
🔔
ShopApp — Flash Sale!
50% off on all electronics today only.
2 min ago

Notifications are one of the most powerful engagement tools in mobile apps. They bring users back even when the app is closed. Used responsibly, they add real value. Used carelessly, they make users uninstall the app.

2. Two Types — Local vs Push

Every mobile notification is one of two fundamentally different types:

📱 Local Notification

Created and triggered entirely by the app itself — no internet required. The app tells the OS: "show this notification now" or "show it at 9am tomorrow". The OS queues it and delivers it.

  • No server involved
  • Works offline
  • App schedules it in advance
  • Immediate or time-based

Examples: alarm clock, daily reminder, "You haven't opened the app in 3 days", countdown timer done

Flutter: flutter_local_notifications

☁️ Push Notification

Sent from a server to the device — requires internet. Your backend sends a message to a notification service (FCM/APNs), which delivers it to the device even if the app is closed.

  • Server triggers it
  • Requires internet
  • Can target specific users
  • Real-time from backend

Examples: new WhatsApp message, order shipped, breaking news alert, promotional offer

Flutter: firebase_messaging (FCM)

Feature Local Notification Push Notification
Triggered by The app itself Your server / backend
Internet needed? No Yes
Works when app is closed? Yes (scheduled ahead of time) Yes
Can target a specific user? No — only the local device Yes — by device token
Setup complexity Simple — one package Requires Firebase project + backend
Flutter package flutter_local_notifications firebase_messaging

3. Android Notification Channels

From Android 8 onwards, every notification must belong to a channel. A channel is a category of notifications. The user can go to app settings and turn off or customise individual channels without disabling all notifications.

For example, a shopping app might have:

Channel ID Channel Name Importance What it shows
orders Order Updates High — makes sound Order placed, shipped, delivered
promotions Promotions & Offers Low — silent Sales, discount codes, new arrivals
reminders Reminders Default Abandoned cart, wishlist restock
iOS does not have channels — it uses a simpler permission model where the user allows or denies all notifications from the app. Channels are Android-only, but flutter_local_notifications handles this difference for you — you define channels and they are simply ignored on iOS.

4. Notification Importance Levels

Each notification (and Android channel) has an importance level that controls how it is presented to the user:

Level Android iOS Priority Behaviour
Max / Urgent Importance.max Critical Makes sound, vibrates, shows as heads-up banner over other apps
High Importance.high High Makes sound, vibrates, shows in notification tray
Default Importance.defaultImportance Default Makes sound, no vibration, shows in tray
Low Importance.low Low No sound, no vibration, silent entry in tray
Min Importance.min Passive No sound, hidden in tray — barely visible

5. Part A — Local Notifications with flutter_local_notifications

Step 1 — Add the package

pubspec.yaml 
dependencies:
  flutter_local_notifications: ^18.0.0
  timezone: ^0.9.4   # needed for scheduled notifications with correct time zones

Step 2 — Create a NotificationService

Following the same pattern as CartDatabase (Lecture 19), we create a service class that handles all notification logic. The rest of the app just calls its methods.

lib/services/notification_service.dart 
import 'package:flutter_local_notifications/flutter_local_notifications.dart';
import 'package:timezone/timezone.dart' as tz;
import 'package:timezone/data/latest.dart' as tz;

class NotificationService {

  // Singleton — one instance, used everywhere
  static final NotificationService instance = NotificationService._internal();
  NotificationService._internal();

  // The core plugin object from the package
  final FlutterLocalNotificationsPlugin _plugin =
      FlutterLocalNotificationsPlugin();

  // ── Initialise ────────────────────────────────────────────────
  // Must be called once — in main() before runApp().
  // Sets up Android channel + iOS permission request.
  Future<void> init() async {
    // Initialise the time zone database (needed for scheduled notifications)
    tz.initializeTimeZones();

    // Android settings: the icon shown in the status bar.
    // '@mipmap/ic_launcher' is the default app icon — always available.
    const android = AndroidInitializationSettings('@mipmap/ic_launcher');

    // iOS settings: ask the user for permission on first launch
    const ios = DarwinInitializationSettings(
      requestAlertPermission: true,
      requestBadgePermission: true,
      requestSoundPermission: true,
    );

    await _plugin.initialize(
      const InitializationSettings(android: android, iOS: ios),
      // onDidReceiveNotificationResponse is called when the user TAPS a notification
      onDidReceiveNotificationResponse: _onNotificationTap,
    );

    // Create the Android notification channel
    await _plugin
        .resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()
        ?.createNotificationChannel(const AndroidNotificationChannel(
          'main_channel',      // channel id
          'Main Notifications', // channel name — shown in Android settings
          description: 'General app notifications',
          importance: Importance.high,
        ));
  }

  // Called when the user taps a notification
  void _onNotificationTap(NotificationResponse response) {
    // response.payload is the string we attached when showing the notification.
    // Use it to decide which screen to open.
    final payload = response.payload;
    print('Notification tapped. Payload: $payload');
    // Navigation logic goes here — see Section 8
  }
}

Step 3 — Request permission on Android 13+

Android 13 (API 33) added a runtime permission for notifications, just like iOS. You need to request it explicitly:

// Add this method to NotificationService
Future<void> requestPermission() async {
  final android = _plugin
      .resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>();
  await android?.requestNotificationsPermission();
}

// Call it early — in main() or on the first screen
await NotificationService.instance.requestPermission();

Step 4 — Initialise in main()

lib/main.dart 
void main() async {
  WidgetsFlutterBinding.ensureInitialized(); // required before any async native call

  await NotificationService.instance.init(); // set up channels + permissions

  runApp(const MyApp());
}

6. Showing Notifications — Three Scenarios

Add these methods to NotificationService:

6a — Immediate Notification (show right now)

// Show a notification instantly.
// Use this after an action — e.g. after the user places an order.
Future<void> showNow({
  required int    id,      // unique number — use a different id per notification type
  required String title,
  required String body,
  String? payload,         // optional data passed back when notification is tapped
}) async {
  await _plugin.show(
    id,
    title,
    body,
    const NotificationDetails(
      android: AndroidNotificationDetails(
        'main_channel',      // must match the channel id created in init()
        'Main Notifications',
        importance: Importance.high,
        priority: Priority.high,
      ),
      iOS: DarwinNotificationDetails(),
    ),
    payload: payload,
  );
}

Usage example — after checkout:

// In cart_screen.dart, after the user taps Checkout
context.read<CartProvider>().clearCart();

await NotificationService.instance.showNow(
  id:      1,
  title:   'Order Placed!',
  body:    'Your order has been confirmed. We will ship it soon.',
  payload: 'order_confirmation',
);

6b — Scheduled Notification (show at a future time)

// Show a notification after a delay.
// Use this for reminders — "You left items in your cart!"
Future<void> scheduleAfter({
  required int      id,
  required String   title,
  required String   body,
  required Duration delay,   // how long from now to wait
  String? payload,
}) async {
  // Convert "now + delay" into a TZDateTime (timezone-aware)
  final when = tz.TZDateTime.now(tz.local).add(delay);

  await _plugin.zonedSchedule(
    id,
    title,
    body,
    when,
    const NotificationDetails(
      android: AndroidNotificationDetails(
        'main_channel', 'Main Notifications',
        importance: Importance.defaultImportance,
      ),
      iOS: DarwinNotificationDetails(),
    ),
    payload: payload,
    androidScheduleMode: AndroidScheduleMode.exactAllowWhileIdle,
    // exactAllowWhileIdle = fire even if the device is in Doze mode
  );
}

Usage example — abandoned cart reminder:

// When user adds item to cart but doesn't checkout,
// schedule a reminder for 1 hour later
await NotificationService.instance.scheduleAfter(
  id:    2,
  title: 'Items waiting in your cart!',
  body:  'You left some items behind. Complete your purchase now.',
  delay: const Duration(hours: 1),
  payload: 'cart_reminder',
);

6c — Cancel a Notification

// Cancel a specific notification by its id
await _plugin.cancel(2); // cancel the cart reminder if user checks out

// Cancel ALL notifications
await _plugin.cancelAll();

7. Handling Notification Taps

When the user taps a notification, your app opens and _onNotificationTap is called with the payload string you attached. You use this payload to navigate to the right screen.

User taps "Order Placed!" notification
↓
App opens (or comes to foreground)
↓
_onNotificationTap(response) is called
↓
response.payload == 'order_confirmation'
↓
Navigate to the Orders screen (or Cart screen)

To navigate from inside NotificationService (which has no BuildContext), the cleanest approach is a global navigator key:

lib/main.dart 
// Declare a global key — gives access to the Navigator from anywhere
final GlobalKey<NavigatorState> navigatorKey = GlobalKey<NavigatorState>();

void main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await NotificationService.instance.init();
  runApp(MaterialApp(
    navigatorKey: navigatorKey, // attach the key to MaterialApp
    home: const SplashScreen(),
  ));
}
lib/services/notification_service.dart — tap handler 
import 'package:flutter_application_2/main.dart'; // for navigatorKey

void _onNotificationTap(NotificationResponse response) {
  final payload = response.payload ?? '';

  switch (payload) {
    case 'order_confirmation':
      // Push to a specific screen using the global navigator
      navigatorKey.currentState?.pushNamed('/cart');
      break;
    case 'cart_reminder':
      navigatorKey.currentState?.pushNamed('/cart');
      break;
    default:
      // Unknown payload — go to home
      navigatorKey.currentState?.pushNamed('/');
  }
}

8. Part B — Push Notifications with Firebase Cloud Messaging (FCM)

Firebase Cloud Messaging (FCM) is Google's free service for sending push notifications to Android and iOS devices. It is the most widely used push notification service in the world.

The Complete Push Notification Flow

Setup (done once)
App installs → registers with FCM → receives a unique device token
App sends token to your backend server → server stores it

Sending a notification
Event happens on server (order placed, new message, sale starts)
↓
Server calls FCM API with: device token + title + body + data
↓
FCM routes the message to the correct device
↓
On Android: FCM delivers directly
On iOS: FCM routes through APNs (Apple Push Notification service)
↓
Notification appears on the user's screen ✅

If the app is in the foreground → onMessage callback fires
If the app is in the background → notification shown in tray; onMessageOpenedApp fires on tap
If the app is terminated → notification shown; check getInitialMessage() on next open

FCM Setup Steps

  1. Create a project on console.firebase.google.com
  2. Add your Flutter app (Android + iOS) to the project
  3. Download google-services.json (Android) and GoogleService-Info.plist (iOS) and place them in the correct folders
  4. Add firebase_core and firebase_messaging to pubspec.yaml
  5. Call Firebase.initializeApp() in main()
pubspec.yaml — FCM packages 
dependencies:
  firebase_core:      ^3.0.0
  firebase_messaging: ^15.0.0

FCM — Handling Messages in Flutter

lib/services/push_notification_service.dart 
import 'package:firebase_messaging/firebase_messaging.dart';
import 'package:firebase_core/firebase_core.dart';

// Top-level function — handles messages when app is TERMINATED (background isolate)
@pragma('vm:entry-point')
Future<void> _firebaseBackgroundHandler(RemoteMessage message) async {
  await Firebase.initializeApp();
  print('Background message: ${message.notification?.title}');
  // Show a local notification here so the user sees it immediately
}

class PushNotificationService {

  final _messaging = FirebaseMessaging.instance;

  // Call this once in main() after Firebase.initializeApp()
  Future<void> init() async {

    // 1. Request permission (required on iOS, optional on Android 13+)
    await _messaging.requestPermission();

    // 2. Get this device's unique FCM token — send it to your backend
    final token = await _messaging.getToken();
    print('FCM token: $token'); // send this to your server

    // 3. Register the background handler
    FirebaseMessaging.onBackgroundMessage(_firebaseBackgroundHandler);

    // 4. Handle messages when the app IS in the foreground
    FirebaseMessaging.onMessage.listen((message) {
      print('Foreground message: ${message.notification?.title}');
      // FCM does NOT automatically show a notification when the app is open.
      // You must display it yourself using flutter_local_notifications.
      NotificationService.instance.showNow(
        id:    99,
        title: message.notification?.title ?? 'New message',
        body:  message.notification?.body  ?? '',
        payload: message.data['screen'],
      );
    });

    // 5. Handle notification TAP when app was in background (not terminated)
    FirebaseMessaging.onMessageOpenedApp.listen((message) {
      print('Notification opened from background: ${message.data}');
      // Navigate based on message.data['screen']
    });

    // 6. Check if the app was opened BY tapping a notification (was terminated)
    final initial = await _messaging.getInitialMessage();
    if (initial != null) {
      print('App opened from terminated via notification: ${initial.data}');
    }
  }
}
Why use both packages together? FCM delivers push messages to the device, but when the app is in the foreground, FCM does NOT show a visible notification automatically — it just calls your onMessage callback. You must manually call flutter_local_notifications to display the banner. This is why real apps use both.

9. Three App States — Which Callback Fires When

App State What happens FCM Callback
Foreground (open & visible) No automatic notification banner — you must show one manually FirebaseMessaging.onMessage
Background (open but not visible) Notification banner shown automatically. If user taps it: FirebaseMessaging.onMessageOpenedApp
Terminated (app process not running) Notification banner shown automatically. If user taps it, app opens and: FirebaseMessaging.getInitialMessage()

10. How Local and Push Work Together

Use Case: User places an order

User taps Checkout in the app
↓
App clears cart → calls Local Notification → "Order placed!" banner appears immediately ✅
↓
App calls backend API → server processes order
↓
Server sends Push Notification via FCM: "Your order has been shipped! 🚚"
↓
Notification arrives even if user has closed the app ✅

Local notification = instant confirmation (no server wait)
Push notification = server-triggered update hours later

11. Best Practices — Being a Good Notification Citizen

Rule Why
Ask for permission at the right moment Asking immediately on first launch gets denied. Ask after the user has seen the app's value — e.g. after they place their first order.
Every notification must provide clear value Vague notifications ("Check out what's new!") get disabled. Specific ones ("Your order has shipped — arrives Friday") get read.
Use the right importance level Not every notification needs to make a sound. Promotional offers should be silent (Importance.low). Order updates should make a sound (Importance.high).
Cancel scheduled notifications when no longer needed If the user checks out, cancel the "abandoned cart" reminder. Stale notifications confuse users.
Always handle the notification tap Tapping a notification that does nothing — or opens the home screen instead of the relevant content — is a broken experience.
Never spam More than 1–2 notifications per day is considered spam. Users who feel spammed will disable notifications or uninstall.

12. Common Mistakes to Avoid

❌ Using a different channel id at show time

// Created channel with id 'main_channel'
// But showing with 'orders' — mismatch!
AndroidNotificationDetails(
  'orders', 'Orders', // ⚠️ channel not created
)

On Android 8+, the notification is silently dropped if the channel doesn't exist.

✅ Channel id must match exactly

// Created:
AndroidNotificationChannel('main_channel', ...)

// Used:
AndroidNotificationDetails(
  'main_channel', // ✅ same id
  'Main Notifications',
)

Always use the exact same string you used when creating the channel.

❌ Reusing the same notification id

// Every product added uses id 1
NotificationService.showNow(id: 1, ...);
NotificationService.showNow(id: 1, ...);
// Second notification REPLACES the first!

Same id = same notification slot. Second call silently replaces the first.

✅ Use unique ids per notification type

// Different id per category
static const int orderNotifId    = 1;
static const int cartReminderId  = 2;
static const int promoNotifId    = 3;

showNow(id: orderNotifId, ...);
showNow(id: cartReminderId, ...); // both visible ✅

Each notification type gets its own reserved id.

❌ Forgetting foreground FCM display

FirebaseMessaging.onMessage.listen((msg) {
  // App is open — do nothing
  // User never sees the notification! ⚠️
});

FCM does not auto-display banners when the app is in the foreground.

✅ Show a local notification manually

FirebaseMessaging.onMessage.listen((msg) {
  NotificationService.instance.showNow(
    id:    99,
    title: msg.notification?.title ?? '',
    body:  msg.notification?.body  ?? '',
  ); // ✅ user sees the banner
});

Use flutter_local_notifications to display FCM messages in the foreground.

Key Takeaway: Local notifications are generated by the app itself and are perfect for reminders, countdowns, and immediate confirmations — no internet, no server. Push notifications are sent by your server via FCM and reach the user even when the app is closed — perfect for real-time events like messages, order updates, and breaking news. Most production apps use both together: local for instant UI feedback, push for server-driven events. Always handle the notification tap to navigate the user to relevant content, and always be respectful — one well-timed, valuable notification is worth more than ten ignored ones.
